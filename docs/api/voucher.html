409: Two distinct cases, separated by code. Branch on the code, not on the status. issue_in_progress: a request with this key is genuinely in flight. Retry with backoff and you will receive the original voucher. Occurs in both modes. issue_stuck: a claim for this key has been pending for more than five minutes, meaning an earlier attempt died mid-issue. In live mode this is not resolved automatically, because money may already have moved and only a human can reconcile it safely. Brontie is alerted when this happens; contact Brontie rather than retrying in a loop, and do not reuse the key. In test mode a stuck claim self-heals after five minutes and the retry succeeds, so issue_stuck is not reproducible with a test key.

429: Rate limited. Honour Retry-After. Limits are per key with separate counters for test and live, so a test key cannot exhaust a live budget. Default 120 requests per minute, burst 20 per second, adjustable per partner without a deploy.

500: Internal error. Always this exact shape, &#123; error, code &#125;, even for a fault deep inside the request. A top-level guard on this route (added after the rest of this spec was first verified) catches anything that would otherwise have escaped as a bare platform error with no code to branch on. For the ordinary case, something failed before any state was touched, or during the mint step itself, any partial work is rolled back before responding: a debit is refunded and the claim released, so retrying with the same key is safe and will succeed. One case is narrower: if the fault happens while this route is already handling an abandoned claim from an earlier attempt (see issue_stuck above), nothing is rolled back on purpose, a debit from that earlier attempt may or may not have gone through, and guessing wrong would either double-charge or lose track of a voucher. "Safe to retry" still holds in the sense that matters: the same key can never mint twice. It does not guarantee the retry succeeds, in this specific case it will most likely come back as 409 issue_stuck rather than a fresh 201, which is the correct outcome, not a bug to work around.
